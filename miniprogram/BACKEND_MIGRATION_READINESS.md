# 独立后端与 MySQL 迁移准备蓝图

> 当前阶段：只做架构准备与接口梳理，不迁移运行中的小程序，不新建服务器或 MySQL。  
> 当前后端：微信云开发云函数 + 云开发文档型数据库。  
> 未来目标：微信原生小程序继续作为主要客户端，后端可逐步切换为独立 HTTP 服务 + MySQL + 对象存储。

## 1. 为什么现在不直接迁移

当前家用版业务稳定，云函数已经承担了权限、下单事务和库存校验。现在直接引入 MySQL、服务器和第二套接口，会让同一份订单在两套数据源之间产生同步风险。

正确顺序是：先固定接口和数据结构，再替换后端实现。小程序页面仍只调用统一业务接口，未来切换时不必重写点菜、购物车和管理页面。

## 2. 当前耦合情况

### 已具备的迁移基础

- 业务数据按 `shopId` 隔离，未来可直接作为多租户字段。
- 顾客、店铺、菜单、订单、库存、权限已经分别由云函数处理。
- 下单、取消订单使用云数据库事务，已有并发库存保护和请求幂等。
- Web 超管后台已经通过 HTTP 访问服务调用 `web-admin`，具备独立后端的调用形态。
- 菜品图片数据库只保存云存储文件 ID，不直接保存二进制内容。

### 需要逐步降低的耦合

- 小程序多数页面和工具函数直接调用 `wx.cloud.callFunction`。
- 云函数 `action` 分发的返回字段尚未完全统一，例如有的直接返回 `orders`，有的返回 `dashboard`。
- `cloud/contracts.js` 只保留了早期部分集合和状态，不能作为完整数据模型来源。
- 顾客扫码会话、云存储临时链接、微信 OpenID 等能力目前依赖云开发实现。

## 3. 目标边界

未来独立后端不改变以下业务规则：

- 一个微信账号对应一个用户账号和唯一系统 ID。
- 所有店铺业务数据必须带 `shopId`，服务端根据身份校验店铺权限。
- 顾客扫码后才获得当前店铺/桌位会话；堂食店提交订单需要有效桌位。
- 库存扣减、创建订单、请求幂等必须在同一个数据库事务中完成。
- 订单菜品、价格、辣度和备注保留订单快照，后续菜单修改不影响历史订单。
- 营业额只统计已完成订单；当天取消订单恢复库存。

未来可替换的实现：云函数改为 HTTP API，云数据库改为 MySQL，云存储改为对象存储；小程序页面的业务规则不应变化。

## 4. 未来接口分层

迁移时增加统一的“业务接口层”，页面只调用接口层，不再各自直接调用 `wx.cloud.callFunction`。

```
小程序页面
    ↓
业务接口层（当前：CloudBase 适配器；未来：HTTP 适配器）
    ↓
云函数 / 独立后端
    ↓
云数据库 / MySQL
```

第一阶段只记录接口，不更改现有调用。第二阶段会优先抽取 `auth`、`shop-access`、`admin-menu` 三类高频接口，保留当前云函数实现作为适配器。

## 5. 当前业务接口清单

| 领域 | 当前云函数 | 关键动作 | 未来 HTTP 资源方向 |
| --- | --- | --- | --- |
| 身份与资料 | `auth` | 登录、当前用户、更新资料 | `/v1/auth`、`/v1/me` |
| 店铺进入 | `shop-access` | 店铺码/桌码进入、重进店铺、当前店铺快照 | `/v1/shop-sessions`、`/v1/shops/current` |
| 顾客菜单和订单 | `admin-menu` | 顾客菜单、创建订单、我的订单 | `/v1/shops/{shopId}/menu`、`/v1/orders` |
| 店铺订单和菜单管理 | `admin-menu` | 完成/取消订单、菜品/分类/库存管理、店铺统计 | `/v1/shops/{shopId}/orders`、`/menu`、`/stats` |
| 店铺现场设置 | `shop-admin` | 营业规则、店铺码、桌位、店内成员 | `/v1/shops/{shopId}/settings`、`/tables`、`/members` |
| 平台超管后台 | `web-admin` | 跨店管理、授权、报表、备份 | `/v1/platform/*` |

未来接口统一返回格式建议为：

```json
{
  "ok": true,
  "code": "OK",
  "message": "",
  "data": {}
}
```

错误时保持 `ok: false`，并使用稳定错误码，例如 `SHOP_CONTEXT_REQUIRED`、`FORBIDDEN`、`OUT_OF_STOCK`。页面只根据错误码决定提示，不依赖中文报错文本。

## 6. 云数据库到 MySQL 的数据映射

| 当前集合 | 未来表 | 迁移说明 |
| --- | --- | --- |
| `users` | `users` | 保留 `openId`、`systemId`、启用状态和全局角色；`open_id`、`system_id` 必须唯一。 |
| `shops` | `shops` | 保留 `shopId`、营业规则、版本号、店铺码哈希。 |
| `shop_members` | `shop_members` | 联合唯一键：`shop_id + user_id`。 |
| `shop_tables` | `shop_tables` | 保留桌号、启用状态、桌码哈希；建议 `shop_id + name` 唯一。 |
| `shop_entry_sessions` | `shop_entry_sessions` 或 Redis | 短期扫码会话；可使用带过期时间的表或 Redis。 |
| `categories` | `categories` | 保留 `shop_id` 和业务分类 ID；建议 `shop_id + name` 唯一。 |
| `dishes` | `dishes` | 保留库存、上下架、售罄、图片对象键与业务菜品 ID。 |
| `orders` | `orders` + `order_items` | 当前订单内嵌菜品快照；MySQL 迁移时拆为订单主表和明细表，但历史快照字段必须完整保留。 |
| `shop_backups` | `shop_backups` | 文件内容放对象存储，MySQL 只保存文件键、范围、大小和创建记录。 |
| `web_admins` | `web_admins` | 密码只保存不可逆哈希，不能导出明文。 |
| `web_sessions` | `web_sessions` 或 Redis | Web 登录会话建议设置过期时间。 |

图片迁移原则：数据库只记录对象键或文件 ID，图片实际文件迁移到对象存储。临时访问 URL 不迁移、不存库，因为它会过期。

## 7. 关键索引与一致性要求

未来 MySQL 至少需要：

- `users(open_id)`、`users(system_id)` 唯一索引；
- `shop_members(shop_id, user_id)` 唯一索引；
- `shop_tables(entry_code_hash)`、`shops(shop_code_hash)` 查找索引；
- `categories(shop_id, name)`、`dishes(shop_id, id)` 唯一或组合索引；
- `orders(shop_id, created_at)`、`orders(owner_user_id, created_at)` 查询索引；
- `orders(shop_id, owner_user_id, request_id)` 唯一索引，防止重复下单。

创建订单时必须在同一 MySQL 事务中完成：检查菜单状态 → 锁定菜品库存 → 扣减库存 → 写入订单与订单明细。支付接入后还需另行设计库存预留和支付回调，不能直接沿用当前免费订单流程。

## 8. 未来迁移步骤

1. **接口准备**：建立统一接口层，原生小程序仍走云函数适配器。
2. **新后端验证**：创建独立后端和 MySQL 测试环境，不接入线上顾客。
3. **数据导出**：导出云数据库集合、云存储图片和店铺 JSON 备份。
4. **数据导入**：按用户、店铺、成员、分类、菜品、桌位、订单的顺序导入测试 MySQL。
5. **数据核对**：核对每店菜品数、桌位数、用户数、订单数、订单金额和图片文件数量。
6. **灰度切换**：先让测试店走新后端，保留云开发作为回退来源。
7. **正式切换**：确认库存、权限和订单一致后，再切换正式店铺。
8. **回滚预案**：若新后端异常，暂停接单并切回经过核对的云函数版本；不得两边同时写订单。

## 9. 当前阶段的完成标准

- 已有完整接口与数据迁移文档。
- 不改动现有顾客、店铺管理员和超管业务流程。
- 不创建或购买服务器、MySQL、域名和对象存储。
- 不将云数据库和 MySQL 同时作为线上写入来源。

下一阶段在用户确认后实施：只新增小程序统一接口层的 CloudBase 适配器，并逐页替换直接 `wx.cloud.callFunction` 调用。该步骤需要单独测试，完成前不碰独立服务器。
