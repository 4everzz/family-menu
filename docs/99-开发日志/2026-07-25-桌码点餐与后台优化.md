# 2026-07-25 桌码点餐与后台优化

## 本次更新概览

本次更新围绕“多商家堂食点餐”的真实使用流程继续完善：顾客进入点餐页后可以直接浏览菜单，通过右上角扫码确认当前桌位；后台订单页更突出桌号，方便店老板或厨房快速识别订单来源；店铺设置页补充固定桌位码与二维码查看能力。

## 主要更新内容

### 1. 点餐页扫码确认桌位

- 点餐页顶部从“家庭点餐”调整为显示当前店铺名。
- 顶部提示改为“当前桌号：暂未扫码 / 当前桌号：X号桌”。
- 右侧圆形入口由“食”改为“扫码”按钮。
- 顾客点击扫码后直接在点餐页确认桌码，不再跳转到单独的“确认桌位”页面。
- 扫码成功后，点餐页保持不跳转，并立即更新当前桌号。

### 2. 删除独立确认桌位页

- 移除 `pages/shop-entry` 页面路由和页面文件。
- 结算页如果发现未确认桌位，不再跳转旧页面，而是提示用户回到点餐页点击“扫码”。
- 桌位校验仍然保留在云函数中，前端只是优化用户流程，不能绕过后端权限判断。

### 3. 固定桌码与二维码管理

- 店铺设置页支持新增、停用、恢复和重置桌位码。
- 新增或重置桌位码后，点击桌码可自动复制。
- 原复制按钮调整为“查看二维码”，用于展示当前新生成的桌码二维码。
- 二维码内容使用 `TABLE:桌位码`，用于当前小程序内扫码确认桌位。
- 修复二维码画布被裁切的问题，改为根据手机屏幕宽度动态计算 canvas 绘制尺寸。

### 4. 后台订单页桌号强化

- 管理订单页中，堂食桌号从普通小字调整为更醒目的绿色标签。
- 目标是让店老板或厨房人员一眼看到“几号桌”，减少出餐和送餐时看错桌位。
- 只调整样式，不改变订单数据结构和云函数逻辑。

### 5. 小程序后台职责边界讨论

- 当前小程序后台适合店老板进行日常操作：菜品、分类、库存、订单、桌码、营业状态。
- 超级管理员更适合未来使用独立 Web 管理后台处理平台级任务：店铺创建、管理员授权、跨店数据、用户搜索、报表导出。
- 暂不立即启动 Web 后台开发，先把该方向写入长期蓝图。

## 技术说明

- 前端框架：微信原生小程序，使用 WXML、WXSS、JavaScript。
- 扫码能力：使用 `wx.scanCode()` 调用微信扫码。
- 桌位确认：前端扫码后调用云函数 `shop-access.joinWithTableCode`，由云端校验桌码是否有效。
- 状态保存：扫码成功后调用 `setCurrentShop()` 更新当前店铺和桌位上下文。
- 二维码展示：使用本地 `weapp-qrcode` 绘制 canvas 二维码，避免开发者工具 npm 构建异常导致页面打不开。
- 后端安全：创建订单时仍由云函数校验当前桌位会话，不能只依赖前端显示的桌号。

## 面试表达

**问题：为什么扫码后不单独跳转确认桌位页？**

回答思路：桌位状态是点餐上下文的一部分，用户扫码后最自然的反馈是留在菜单页并看到当前桌号。因此将桌码确认整合到点餐页，减少页面跳转和重复状态，同时后端继续通过云函数校验桌码，保证安全性。

**问题：为什么后台订单页要突出桌号？**

回答思路：堂食订单中桌号是厨房和店老板处理订单的核心信息。通过视觉层级强化桌号，可以提升后台页面的可扫读性，减少出餐和送餐时的误判。

**问题：为什么超级管理员后台未来更适合做成 Web？**

回答思路：小程序适合现场高频操作，例如接单、改库存、管理桌码；平台级管理需要搜索、分页、批量操作、报表和跨店数据处理，更适合 Web 后台。这样可以把店铺日常管理和平台运营管理拆开，权限边界更清楚。

## 我这次应该记住什么

- 扫码只是前端入口，真正的桌码有效性必须由云函数校验。
- 页面不是越多越好，能在原流程内完成的状态更新，通常比跳转新页面更顺。
- 后台页面要突出关键业务信息，例如堂食场景里的桌号。
- 小程序适合移动端现场管理，Web 后台更适合平台级复杂管理。
