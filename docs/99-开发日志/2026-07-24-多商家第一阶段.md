# 2026-07-24 多商家第一阶段

## 本次完成内容

项目从单个家庭菜单升级为多商家架构的第一阶段。核心目标是让一套小程序支持多家独立店铺，同时确保不同店铺的菜单、订单、库存和管理数据不会互相看到或修改。

### 1. 默认家庭店与旧数据迁移

- 新建默认“家庭店”，并将原有分类、菜品、订单补充 `shopId`。
- 现有用户与家庭店建立成员关系，避免旧菜单和历史订单丢失。
- 迁移后家庭店仍可正常点菜、下单和管理。

### 2. 店铺数据隔离

- 新增 `shops`、`shop_members`、`shop_tables` 云数据库集合。
- 菜品、分类、订单等业务数据按 `shopId` 隔离。
- 云函数从成员关系判断用户能否访问目标店铺，前端传来的 `shopId` 不能单独决定权限。
- 创建订单和扣减库存的事务也附加店铺范围，避免跨店读取或写入。

### 3. 店铺进入与创建

- 顾客通过店铺码或二维码进入对应店铺，不提供店铺广场和手动店铺切换。
- 进入另一家实体店时自动清空购物车，防止把 A 店菜品提交到 B 店。
- 超级管理员可以创建空白新店；新店不复制家庭店的菜品、库存和订单。
- 店铺码采用一次性明文展示，云数据库仅保存 SHA-256 哈希，降低店铺码泄露后的风险。

### 4. 店铺营业规则

- 店铺管理员可手动暂停或恢复接单。
- 可配置指定日期不营业。
- 顾客在暂停接单或不营业日仍可浏览菜单、加入购物车，但云函数拒绝创建订单。
- 时间判断统一以 `Asia/Shanghai` 北京时间为准，而不是依赖顾客手机时间。

### 5. 顾客备注简化

- 菜品详情移除“少油、少盐”等快捷标签。
- 保留一个自由备注输入框，减少不适用于所有菜品的固定选项。

## 学习记录

### 全局用户与店铺成员的分离

`users` 保存一个人的全局身份资料，`shop_members` 保存该人与某家店的关系和店内角色。这样同一个人可以在 A 店是顾客，在 B 店是管理员，权限不会混在一起。

这是企业项目常见的“用户身份”和“租户成员关系”分离设计，属于权限控制与架构设计。

### 服务端租户鉴权

前端可以告诉服务端“我当前在这家店”，但服务端必须自己查询该用户是否属于该店，再附加 `shopId` 查询条件。这个过程叫服务端鉴权和多租户数据隔离。

### Web 后台与小程序职责拆分

小程序适合顾客点餐和店铺现场高频操作；大量用户筛选、跨店订单查询、报表、导出等复杂工作更适合后续的 Web 管理后台。先复用现有云函数和数据模型，可以避免为管理页面过早重构整个系统。

## 面试表达

**问题：如何保证多商家之间的数据不会串店？**

回答思路：所有店铺业务数据都加 `shopId`。云函数根据微信身份读取 `shop_members`，确认成员角色和店铺归属，再在每次查询、更新、删除和库存事务中强制附加 `shopId` 条件。即使有人修改前端参数，也无法直接读取或修改其他店铺的数据。
