# 2026-07-24 多商家第一阶段

## 本次完成内容

项目从单个家庭菜单升级为多商家架构的第一阶段。核心目标是让一套小程序支持多家独立店铺，同时确保不同店铺的菜单、订单、库存和管理数据不会互相看到或修改。

### 1. 默认家庭店与旧数据迁移

- 新建默认“家庭店”，并将原有分类、菜品、订单补充 `shopId`。
- 现有用户与家庭店建立成员关系，避免旧菜单和历史订单丢失。
- 迁移后家庭店仍可正常点菜、下单和管理。

### 2. 店铺数据隔离

- 新增 `shops`、`shop_members`、`shop_tables` 云数据库集合。
- 菜品、分类、订单等业务数据按 `shopId` 隔离。
- 云函数从成员关系判断用户能否访问目标店铺，前端传来的 `shopId` 不能单独决定权限。
- 创建订单和扣减库存的事务也附加店铺范围，避免跨店读取或写入。

### 3. 店铺进入与创建

- 顾客通过店铺码或二维码进入对应店铺，不提供店铺广场和手动店铺切换。
- 进入另一家实体店时自动清空购物车，防止把 A 店菜品提交到 B 店。
- 超级管理员可以创建空白新店；新店不复制家庭店的菜品、库存和订单。
- 店铺码采用一次性明文展示，云数据库仅保存 SHA-256 哈希，降低店铺码泄露后的风险。

### 4. 店铺营业规则

- 店铺管理员可手动暂停或恢复接单。
- 可配置指定日期不营业。
- 顾客在暂停接单或不营业日仍可浏览菜单、加入购物车，但云函数拒绝创建订单。
- 时间判断统一以 `Asia/Shanghai` 北京时间为准，而不是依赖顾客手机时间。

### 5. 顾客备注简化

- 菜品详情移除“少油、少盐”等快捷标签。
- 保留一个自由备注输入框，减少不适用于所有菜品的固定选项。

### 6. 固定桌码与短期扫码会话

- 桌码继续采用可长期打印张贴的固定二维码，不使用动态桌码。
- 顾客扫描店铺码或桌码后，云端创建有效期为 2 小时的 `shop_entry_sessions` 扫码会话。
- 会话绑定用户、店铺和桌位；数据库只保存随机令牌的 SHA-256 哈希。
- 菜单读取、提交订单、查看当前店铺订单均由云函数校验扫码会话，不再仅依赖客户端保存的 `shopId` 或历史顾客成员关系。
- 顾客扫码进入另一家店会清空购物车；扫码无效、会话过期或桌位停用时也会清空当前点餐上下文。
- 顾客重新打开小程序后需要重新扫码；店铺管理员仍使用 `shop_members` 进行本店管理授权。

### 7. 固定桌位码管理

- 店铺设置新增堂食桌位管理，可新增桌位、停用或恢复桌位、重置桌位码。
- 桌位码与店铺码共用 8 位字母数字格式，生成时同时检查 `shops` 与 `shop_tables`，避免入口码冲突。
- 数据库只保存桌位码哈希；新增或重置时仅展示一次新码并自动复制，便于后续生成固定打印二维码。
- 停用桌位后，顾客的旧桌位会话由云函数拒绝，不能继续下单。

## 已完成验证

- 新测试店创建成功，且初始菜单、订单和库存为空，与家庭店数据隔离。
- 顾客不能在小程序中主动切换到其他店铺。
- 简化后的顾客备注功能已验证正常。

## 当前等待验证

营业规则需要继续进行真机或体验版验证：

1. 暂停接单后，顾客可浏览和加购，但提交订单会被拒绝。
2. 设置当天不营业后，提交订单同样会被拒绝。
3. 恢复接单或移除关闭日期后，订单可正常创建。
4. 重置店铺码后，旧码失效，新码可进入。
5. 创建 `shop_entry_sessions` 集合后，验证顾客重启小程序、无效扫码、跨店扫码和会话过期时都不能回退到旧店下单。
6. 新增桌位、复制桌位码、停用/恢复桌位、重置桌位码；确认旧码失效，新码可扫码进入。

## 学习记录

### 全局用户与店铺成员的分离

`users` 保存一个人的全局身份资料，`shop_members` 保存工作人员与某家店的关系和店内角色。顾客不再因为曾经扫码就长期拥有店铺访问资格，而是使用短期扫码会话进入当前店铺。

这是企业项目常见的“用户身份”和“租户成员关系”分离设计，属于权限控制与架构设计。

### 服务端租户鉴权

前端可以告诉服务端“我当前在这家店”，但服务端必须自行校验：工作人员是否属于该店，或顾客的扫码会话是否属于该店且尚未失效，再附加 `shopId` 查询条件。这个过程叫服务端鉴权和多租户数据隔离。

### 固定桌码与短期会话

固定桌码适合打印张贴，二维码本身不需要频繁更换。扫码会话解决的是“上次进入 A 店后，不能在 B 店扫码失败时回退到 A 店继续下单”的问题，不负责证明顾客真实位置。未来接入支付后，订单应先支付成功才进入制作和扣库存，支付承担最终的反恶意下单控制。

### Web 后台与小程序职责拆分

小程序适合顾客点餐和店铺现场高频操作；大量用户筛选、跨店订单查询、报表、导出等复杂工作更适合后续的 Web 管理后台。先复用现有云函数和数据模型，可以避免为管理页面过早重构整个系统。

## 面试表达

**问题：如何保证多商家之间的数据不会串店？**

回答思路：所有店铺业务数据都加 `shopId`。工作人员操作时，云函数根据微信身份读取 `shop_members`；顾客操作时，云函数校验短期扫码会话是否绑定当前用户、店铺和桌位。每次查询、更新、删除和库存事务都强制附加 `shopId` 条件。即使有人修改前端参数，也无法直接读取或修改其他店铺的数据。
