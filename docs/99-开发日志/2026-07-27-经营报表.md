# 2026-07-27 经营报表

## 本次目标

在小程序店铺后台新增“基础经营报表”，让店老板在手机上快速查看近一段时间的经营情况，而不是只能看到后台首页的“今日概览”。同时明确本阶段先做小程序端报表、暂不启动 Web 后台。

## 完成内容

### 1. 云函数新增统计接口 getShopStats

- 在 `admin-menu` 云函数中新增 `getShopStats` action，支持近 7 天 / 近 30 天两种时间范围。
- 统计维度：区间总订单数、总营业额、平均客单价、完成率、桌码订单占比、已完成订单数。
- 每日明细：按北京时间逐日聚合订单数与营业额，返回连续日期序列（无订单的日期补 0，保证图表不断档）。
- 热销排行：按销量排序返回 Top10，同时带出每个菜品的累计销量和销售额。
- 查询严格按 `shopId` 过滤，并复用现有 `getShopContext(user, event, true)` 做店铺管理员校验，隔离与权限规则未改动。

### 2. 新建报表页面 pages/admin-stats

- 新增页面四件套（wxml/wxss/js/json），注册进 `app.json`。
- 顶部提供“近7天 / 近30天”切换页签，切换即重新拉取数据。
- 汇总区用六格指标卡展示核心数字。
- 每日营业额用纯 WXSS 横向条形图呈现（按区间内最大值归一化），不引入第三方图表库，避免开发者工具 npm 构建异常导致页面打不开。
- 热销菜品排行榜，前三名序号高亮。
- 页面样式沿用现有 admin 页面的红色主题与卡片风格，保持后台视觉一致。

### 3. 后台入口接入

- 管理中心（admin-menu）新增“经营报表”按钮，位于“店铺设置”旁。
- 复用现有 `navigatingTarget` 防抖跳转逻辑，避免重复点击。

## 遇到的问题与处理

- 后台首页已有“今日概览”，为避免重复，报表页定位为“趋势与区间汇总”：每日走势、平均客单价、完成率、桌码占比等增量指标。
- 图表实现放弃引入图表库，改用 WXSS 条形图，降低构建风险，也让页面更轻。
- 关于“报表放小程序还是先做网页端”，结论是先放小程序：受众是店老板、现场手机查看，且小程序已有登录与权限体系，成本低；网页端待出现导出、跨店分析等小程序做不好的需求时再启动，届时统计云函数可直接复用。

## 学习收获

- 报表类需求先想清楚“和已有展示的差异点”，避免重复造指标。
- 连续日期序列要在服务端预填充补 0，前端图表才不会因缺失日期而错位。
- 统计接口同样要走 shopId 隔离和管理员校验，不能因为“只是读数据”就放松权限边界。

## 面试表达

**问题：经营报表为什么放在小程序而不是先做 Web 后台？**

回答思路：报表的第一用户是店老板，典型场景是在店里用手机随手查看经营情况，小程序已有登录、店铺上下文和权限体系，加一个云函数接口和一个页面即可上线。Web 后台面向平台级管理（跨店、导出、批量），成本高，适合在出现小程序做不好的需求时再启动，且统计逻辑可复用。

**问题：每日营业额趋势为什么要在服务端补齐日期？**

回答思路：如果只返回有订单的日期，前端画趋势图时缺失的日期会被跳过，导致时间轴不连续、图形失真。服务端按区间生成连续日期并对无订单日补 0，前端渲染更简单也更准确。

## 简历价值

> 为多商家点餐系统设计并实现店铺经营报表：云函数按 shopId 隔离聚合近 7/30 天订单数据，输出营业额趋势、客单价、完成率、渠道占比与热销排行；小程序端以纯 WXSS 图表呈现，兼顾轻量与构建稳定性。
