# 2026-07-27 web-admin 网页后台后端接口

## 本次目标

启动「超级管理员网页端」的后端。目标是让平台级管理（建店、跨店授权、跨店数据）从小程序里剥离出来，放到一个独立的网页后台，用**账号密码**登录，而不是复用小程序的微信登录。本次只做后端云函数 `web-admin`，前端页面另做。

同时确定了整体路线：网页端前端用开源模板（Soybean Admin），后端暂用微信云开发，接口层写干净，方便日后小程序迁 uni-app、数据库换成更大的 SQL 库时前端不用重写。

## 完成内容

### 1. 独立云函数 web-admin 与双入口兼容

- 新建 `cloudfunctions/web-admin`，与小程序云函数完全独立，避免把网页鉴权逻辑混进 `admin-menu` / `shop-admin`。
- 请求解析 `parseRequest` 同时兼容两种调用方式：云开发「HTTP 访问服务」（`event` 带 `httpMethod`/`body`）和 `wx.cloud.callFunction`（`event` 即业务参数），后者方便本地联调。
- HTTP 入口统一处理 CORS 预检（`OPTIONS`）、跨域头、JSON 响应封装。

### 2. 账号密码鉴权（不依赖微信身份）

- `setup`：一次性初始化入口，仅当 `web_admins` 集合为空时可用，用于设定第一个超管账号，避免公开的注册接口。
- `login`：校验账号密码，成功后签发随机 token，会话写入 `web_sessions`（存 token 哈希、有效期 2 小时）。
- 密码用 **pbkdf2**（sha256、10 万次迭代、随机盐）存哈希，绝不存明文；校验用 `timingSafeEqual` 做定长比较。账号不存在时也走一次哈希、统一返回「账号或密码错误」，降低时序差异与账号存在性泄露。
- `requireSuperAdmin(token)`：除 `setup`/`login`/`logout` 外的所有操作都要带有效且未过期的会话，过期返回 401。

### 3. 三大业务接口

**店铺管理（#10）**

- `listShops`：返回全部店铺，并聚合每店的一级/二级管理员人数。
- `createShop`：建店 + 返回一次性店铺码。**网页超管没有微信身份，因此不像小程序那样把创建者自动设为店长**，建完店后通过「授权」把某个微信用户指定为一级。
- `setShopEnabled`：停用/启用店铺。

**成员授权与用户搜索（#11）**

- `searchUsers`：按昵称模糊、systemId 精确、文档 ID 三种方式搜索用户，可带 `shopId` 标注该用户在这家店的当前权限。
- `listShopMembers`：列出某店的一级/二级管理员，附头像、昵称、systemId。
- `grantRole` / `revokeRole`：指定或撤销一级/二级。网页超管可直接授予一级（对应小程序里「只有超管能设一级」的规则）。

**跨店数据总览（#12）**

- `getPlatformOverview`：店铺总数/启用数、用户数、一二级管理员数；今日跨店订单数、营业额、完成数；今日营业额 Top10 店铺。

### 4. 复用小程序既有口径与安全约束

- systemId 生成/补齐、店铺码去重、角色归一化都沿用小程序 `shop-admin` 的同一套逻辑，保证网页端和小程序对同一份数据的理解一致。
- 头像统一走 `getTempFileURL` 换临时链接，绝不把 `cloud://` 直接返回给前端。
- 统计口径（金额取 `order.total`、状态 `已完成`、按北京时间当日范围 `createdAtServer`）与小程序经营报表一致，避免两端对不上账。

## 遇到的问题与处理

- **网页超管无 openId**：小程序建店会把创建者写成店长，但网页超管不是微信用户。处理办法是网页建店只创建店铺、不挂成员，店长由后续「授权」步骤指定。
- **账号存在性泄露**：登录失败若因账号不存在而更快返回，会被用来枚举账号。处理办法是账号不存在时也执行一次哈希、统一错误提示。
- **`*` 跨域仅用于联调**：`ALLOWED_ORIGINS` 暂为 `*`，正式部署要收紧到静态托管的域名，已在代码注释和验收清单里标注。

## 学习收获

- 网页端和小程序端最大的差别是**身份来源**：小程序有 openId，网页端得自建账号体系（账号密码 + 会话 token），鉴权不能想当然复用。
- 密码存储要点：加盐、慢哈希（pbkdf2/bcrypt）、定长比较、统一错误提示，一个都不能少。
- 多端共用一份数据时，统计和角色口径必须集中、一致，否则两端会对不上账；宁可复制同一套归一化函数，也不要各写一套。

## 面试表达

**问题：网页后台为什么不复用小程序的登录，而要另做账号密码？**

回答思路：小程序登录依赖微信 `wx.login` 拿 openId，网页端没有这个能力。平台超管也不该和某个微信号绑定。所以网页端自建账号体系：账号密码登录，服务端校验后签发会话 token，密码用 pbkdf2 加盐哈希存储，后续请求带 token 校验会话。这也让后端未来脱离微信云开发、迁到独立服务器时不受影响。

**问题：怎么防止登录接口被用来枚举账号？**

回答思路：无论账号是否存在都执行一次密码哈希，返回统一的「账号或密码错误」，并用定长比较（timingSafeEqual）避免时序差异，让攻击者无法从响应快慢或提示文案区分账号是否存在。

### 联调踩的两个坑

- **Shops.vue 一直转圈加载不出来**：现象是店铺管理页永远停在「正在加载」，而用同一个 `listShops` 接口的授权页却正常。排查时先被浏览器插件注入的 `content_main.js` 报错误导（那是插件的、与本项目无关）；真正决定性的证据是 **Network 面板里根本没有发往后端的请求**。原因是 `Shops.vue` 里 `loading` 初始值为 `true`，而**漏写了 `onMounted(load)`**，进页面时压根没触发加载，所以永远停在初始 loading 态。补上 `onMounted(load)` 后正常。
  - 教训：`loading` 初始给 `true` 时，一旦忘了触发加载就会「假装在加载」且没有任何报错，很有迷惑性；排查这类「卡加载」优先看 Network 有没有真发出请求，而不是盯控制台红字（还要先排除浏览器插件的噪音）。
- **请求可能永久挂起**：`fetch` 默认没有超时，后端/网络一卡就无限转圈。给 `api.js` 的每个请求加了 15 秒 `AbortController` 超时，超时返回明确错误提示而不是一直转。
