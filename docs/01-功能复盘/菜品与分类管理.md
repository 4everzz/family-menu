# 菜品与分类管理

## 这次改动解决了什么问题

管理员需要在手机端维护菜品和分类，包括新增菜品、修改价格和简介、更换图片、上架下架、售罄、库存设置，以及删除不再使用的菜品和空分类。

分类不能直接随意删除，因为分类下可能还有菜品。删除后菜品会失去分类，后续编辑或点餐会出错。因此现在只允许删除没有菜品的空分类。

## 改了什么

- 菜品资料、状态和库存集中在同一个编辑页保存。
- 支持管理菜品图片、简介、价格、分类、辣度、库存、上下架和手动售罄。
- 支持永久删除菜品，并保留历史订单内的菜品快照。
- 分类支持新增、修改和删除；云函数会检查分类是否仍被菜品引用。
- 管理页针对手机端修复双列布局，辣度和分类卡片不会超出屏幕。

## 用了什么框架/技术

通俗说，管理页面负责收集管理员输入；真正修改数据时，页面会请求云函数，由云函数检查权限和数据合法性后再写入数据库。

专业上使用微信原生小程序的 WXML、WXSS、JavaScript，以及云函数的服务端校验。页面布局使用 Flex 双列换行，保证不同手机宽度下卡片不会溢出。

## 为什么这样设计

- 菜品资料一次保存，避免价格、状态和库存分散在多个入口造成重复逻辑。
- 删除分类前由云函数再检查一次菜品引用，前端提示不能代替服务端保护。
- 已删除菜品不影响历史订单，因为订单已保存快照。
- 手机端优先使用兼容性更好的 Flex 布局，避免部分微信客户端对嵌套 Grid 宽度计算不稳定。

## 企业项目归类

前端工作常用、后端工作常用、云开发工作常用、数据完整性设计。

## 面试官可能怎么问

**问题：为什么删除分类前要检查是否有菜品？**

**初级/实习回答思路：** 分类和菜品存在引用关系。如果直接删除，菜品会变成无效数据。因此前端可以提示，但云函数也必须查询菜品是否使用该分类；只有空分类才能删除。这是保护数据完整性。

**问题：为什么手机端不用 Grid，而改为 Flex？**

**初级/实习回答思路：** 设计目标是稳定双列且不横向溢出。实际真机测试发现部分环境中嵌套 Grid 宽度计算异常，所以改为 Flex 换行并显式限制每项宽度。工程上以真实兼容性结果为准。

## 我这次应该记住什么

- 删除操作必须考虑关联数据，不能只删当前记录。
- 前端校验改善体验，服务端校验负责安全。
- 手机端布局要以真机测试为准，不能只看开发者工具模拟器。
