# 多商家与跨端演进路线图

## 0. 决策摘要

项目下一阶段的架构目标是“多商家独立使用”，采用一套小程序和一套云端服务支持多家店铺，而不是为每家店复制一套代码。专业名称是“多租户架构”。正式项目定位为“基于微信小程序云开发的多商家餐饮点餐管理系统”。

当前不实施代码重构，不迁移 MySQL、独立后端或 uni-app。实施顺序固定为：先完成当前家庭版稳定验收，再完成多商家架构与基础经营报表；微信版业务稳定后评估 uni-app；只有复杂报表、多端统一后端等需求明确时，最后评估独立后端与 MySQL。

## 1. 当前基础与目标边界

### 当前基础

- 客户端：微信原生小程序，使用 WXML、WXSS 和 JavaScript。
- 服务端：微信云开发云函数。
- 数据库：微信云开发数据库。
- 现有业务集合：`users`、`categories`、`dishes`、`orders`。
- 现有能力：微信身份登录、角色权限、菜品分类、库存、订单流转和管理员管理。

### 多商家目标

- A 店只能看到和操作 A 店的菜单、菜品、订单、库存和经营数据。
- B 店不能通过前端参数、页面跳转或云函数调用读取 A 店数据。
- 平台超级管理员可管理店铺和店铺管理员；店铺管理员只管理自己店铺。
- 同一用户未来可加入多家店，但每次操作必须明确归属某一家店。
- 旧家庭版数据完整迁入“默认家庭店”，不丢失历史订单。

### 本阶段不做

- 不接入真实支付、配送、外卖平台。
- 不提前迁移 MySQL、Redis、服务器或 Web 管理后台。
- 不把小程序整体迁到 uni-app。
- 不一次性重写全部页面。

## 2. 目标数据模型

多租户最关键的规则是：所有店铺业务数据都要有 `shopId`，并且云函数必须从登录用户的权限关系中确认其可访问的店铺，不能只相信前端传来的 `shopId`。

### 建议新增集合

| 集合 | 作用 | 关键字段 |
| --- | --- | --- |
| `shops` | 店铺基础信息 | `id`、`name`、`status`、`ownerUserId`、`createdAt` |
| `shop_members` | 用户与店铺的成员关系和角色 | `shopId`、`userId`、`role`、`enabled`、`createdAt` |

### 现有集合的演进

| 集合 | 新增或调整字段 | 目的 |
| --- | --- | --- |
| `users` | 保留全局身份资料，不再以全局管理员角色作为店铺权限唯一来源 | 一个微信用户可加入多家店 |
| `categories` | `shopId` | 分类仅属于一家店 |
| `dishes` | `shopId` | 菜品、图片和库存仅属于一家店 |
| `orders` | `shopId` | 订单、库存扣减、历史订单按店铺隔离 |

### 角色设计

| 角色 | 权限范围 |
| --- | --- |
| 普通顾客 | 在加入的店铺点菜、查看自己的订单 |
| 店铺厨师 | 查看本店制作中的订单并完成订单 |
| 店铺管理员 | 管理本店菜品、分类、库存、订单和店铺成员 |
| 平台超级管理员 | 创建店铺、指定店铺管理员、处理跨店问题 |

现有 `manager` 和 `super_admin` 需要在正式迁移时重新映射：平台超级管理员保留在全局用户身份中；店铺管理员和厨师放入 `shop_members`，避免一个店铺管理员自动获得其他店铺权限。

## 3. 服务端与权限设计

### 云函数访问流程

每个涉及店铺数据的云函数都遵循同一流程：

1. 根据微信 OpenID 读取当前登录用户。
2. 从服务端读取该用户与目标店铺的 `shop_members` 关系。
3. 校验成员是否启用、角色是否允许当前操作。
4. 查询、写入、更新和删除时同时附加 `shopId` 条件。
5. 订单、库存等敏感写操作继续使用事务，保证同店库存不会被并发超卖。

前端可以提交“当前店铺”的选择，但只能作为请求参数；最终权限判断必须在云函数执行。这是后端工作和面试中常说的“服务端鉴权”和“租户隔离”。

### 接口演进原则

- 为现有菜单、订单、菜品、分类接口补充 `shopId` 上下文，而不是在页面内复制查询代码。
- 将店铺上下文读取封装为公共云函数辅助方法，避免每个接口重复写权限逻辑。
- 新旧接口在迁移期保持兼容；旧数据迁移完成并验收后，再逐步删除兼容分支。
- 所有管理写操作继续由云函数执行，客户端不直接写关键集合。

## 4. 分阶段实施计划

### 阶段 A：当前家庭版稳定验收

**目标：** 在不改变架构的前提下，确认登录、点菜、库存、订单、管理端和图片在真机及体验版稳定可用。

**完成标准：**

- 顾客、厨师、管理员三个典型流程各完成一次真机测试。
- 菜品上下架、售罄、库存扣减、订单完成、历史订单均有验收记录。
- 当前数据库集合完成备份说明，云函数版本与 Gitee 提交号可追溯。

### 阶段 B：多商家方案评审

**目标：** 先输出方案，不写业务重构代码。

**要确认的决定：**

- 第一批需要支持几家店、每家店有哪些角色。
- 顾客如何进入店铺：扫码进入、店铺邀请码或默认家庭店。
- 一个用户是否允许加入多店，以及默认店铺如何保存。
- 菜品图片是否按店铺目录组织。
- 平台超级管理员由谁担任，如何处理店铺成员离职或停用。

**交付物：** 数据字段清单、权限矩阵、接口清单、迁移脚本设计、测试用例和回滚方案。用户确认后才进入下一阶段。

### 阶段 C：店铺基础数据与旧数据迁移

**目标：** 创建店铺与成员关系，让旧家庭版成为第一家默认店铺。

**实施步骤：**

1. 导出现有 `users`、`categories`、`dishes`、`orders` 备份。
2. 创建一条默认店铺数据，例如“家庭店”。
3. 为现有超级管理员创建该店铺的管理员成员关系。
4. 为现有数据批量补充默认 `shopId`。
5. 校验迁移前后菜品、分类、订单数量一致。
6. 保留迁移日志和备份，在验收前不删除旧兼容字段。

**风险与控制：**

- 批量更新必须分批执行并记录成功、失败数量。
- 迁移期间暂停管理端写入，避免新旧数据混写。
- 出现数量不一致时立即停止切换，用备份与迁移日志回滚，不继续修补线上数据。

### 阶段 D：云函数租户隔离

**目标：** 先在服务端完成数据隔离，再开放页面入口。

**实施步骤：**

1. 创建统一的“当前用户 + 当前店铺 + 成员角色”鉴权辅助方法。
2. 改造菜单、菜品、分类、订单、库存、用户管理的读取接口，强制按 `shopId` 查询。
3. 改造新增、修改、删除接口，服务端写入 `shopId`，不接受跨店写入。
4. 为库存扣减、订单完成等事务补充店铺条件。
5. 针对普通顾客、厨师、店铺管理员、平台超级管理员编写权限拒绝测试。

**完成标准：** 任意角色手工构造其他店铺 ID 时，云函数仍拒绝读取和写入。

### 阶段 E：小程序店铺上下文与管理界面

**目标：** 让用户可以明确地进入和切换正确店铺。

**实施步骤：**

1. 增加店铺选择或扫码进入流程。
2. 菜单、购物车、订单和“我的”页展示当前店铺名称。
3. 切换店铺时清空购物车，防止把 A 店菜品提交到 B 店。
4. 店铺管理员页面只展示本店的菜品、分类、订单、库存和成员。
5. 平台超级管理员新增店铺和授权店铺管理员。

**完成标准：** 两家测试店同时存在时，页面、订单和库存完全隔离。

### 阶段 F：基础经营报表

**目标：** 在店铺隔离稳定后，提供最小可用经营数据。

**第一版指标：** 今日订单数、今日营业额、已完成订单数、售罄菜品数、销量前五菜品。

**原则：** 报表先按单店查询，禁止默认跨店聚合；只有平台超级管理员才可查看跨店汇总。若云开发数据库在复杂聚合或历史数据规模上无法满足，再评估 MySQL。

### 阶段 G：多商家验收与上线

**测试矩阵：**

- 两家店、两名店铺管理员、两名顾客。
- 同名菜品和不同价格，确认不会串店。
- 同一顾客切换店铺、清空购物车、重新下单。
- 跨店 URL、跨店云函数参数、禁用成员、停用店铺的拒绝测试。
- 订单库存并发提交与每日重置测试。
- 旧家庭店历史订单、图片和库存数据的回归测试。

**上线与回滚：** 先发布体验版给少量测试店，验证通过后再扩大范围；保留迁移前备份、迁移日志和兼容读取分支，出现隔离问题时立即限制新店写入并回滚到最近可用版本。

## 5. MySQL 评估门槛

以下情况出现时，再正式评估 MySQL，而不是提前迁移：

- 需要大量按日期、菜品、门店、员工维度的复杂报表。
- 跨店数据量持续增长，云开发数据库查询与聚合难以维护。
- 需要 Web 管理后台、外部系统或多个客户端共享同一后端。
- 需要更成熟的数据库备份、审计、读写分离或数据分析能力。

迁移 MySQL 时应保持云函数或独立后端接口不变，让小程序前端不直接依赖数据库类型。这是“接口隔离”的实践，能降低替换基础设施的成本。

## 6. 第二阶段：uni-app 评估与迁移计划

多商家版本稳定后，只有确认需要 App、H5 或其他小程序端时才评估 uni-app。

### 迁移前条件

- 业务规则已主要集中在云函数和公共工具模块。
- 多店铺权限、订单、库存接口已稳定并有测试。
- 当前原生小程序页面没有频繁大改。
- 明确至少一个新增运行端的业务价值，而不是只为使用新框架而迁移。

### 迁移方式

1. 先做一页非关键页面试点，例如“我的”或历史订单。
2. 保持同一套云函数接口与数据库，不同时更换前端框架和后端。
3. 验证样式、登录、图片、分包、性能和真机兼容。
4. 按页面逐步迁移，不进行一次性全量重写。

这种做法在企业中叫“渐进式迁移”，核心目的是控制风险和保持可回退能力。

## 7. 简历与面试表达

项目以一个主项目、三个阶段演进的方式呈现：

1. 第一阶段：微信原生小程序 + 云开发，完成点餐、订单、库存、权限和多商家基础能力。
2. 第二阶段：uni-app 跨端迁移，实现多端运行。
3. 第三阶段：独立后端 + MySQL 架构升级，支撑复杂报表和多端统一后端。

多店铺架构完成后，可将项目描述为：

> 基于微信云开发设计多租户点餐系统，通过 `shopId` 实现菜单、订单、库存的数据隔离；将店铺成员角色校验放在云函数，实现服务端鉴权和跨店访问拦截；使用事务保证库存扣减与订单创建的一致性，并通过分阶段迁移将单店家庭版平滑演进为多店系统。

**面试常问：** 如何保证多租户数据隔离？回答重点是：数据表或集合带 `shopId`、每次服务端查询强制附加 `shopId`、权限关系由服务端读取、敏感写操作使用事务、跨租户访问必须有自动化和手工测试。

## 8. 第三阶段启动前评审要求

只有满足以下任一条件时才启动第三阶段评估：复杂经营报表已超出云开发数据库的维护边界、多个客户端需要统一后端、外部系统需要标准化接口，或多商家规模已经使现有架构难以维护。评估必须先明确后端语言和框架、MySQL 数据迁移方案、接口兼容策略、数据备份和回滚方案。

## 9. 多商家改造启动条件

在没有以下确认前，不启动多店铺代码改造：

1. 当前家庭版关键流程完成稳定验收。
2. 用户确认第一批店铺数量、店铺进入方式和角色规则。
3. 现有云数据库完成可恢复备份。
4. 数据迁移、权限测试和回滚方案通过评审。
