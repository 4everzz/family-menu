# 小家菜馆子家庭版微信小程序蓝图

## 项目定位

当前这是一个供家庭堂食使用的微信小程序。顾客通过微信身份登录后浏览菜单、点菜和查看自己的订单；管理员在同一个小程序内维护菜品、分类和订单。第一阶段不接入真实支付、外卖或公开商业运营。

项目的长期定位是“基于微信小程序云开发的多商家餐饮点餐管理系统”：先在微信原生小程序和微信云开发体系内完成多商家能力，再逐步评估跨端和独立后端升级。

## 正式登录与权限规则

- 所有人必须先使用微信登录，系统会以微信 OpenID 自动创建并绑定一个用户账号。
- 不支持游客下单、游客查看订单、自定义账号或账号密码登录。
- 当前不接入手机号授权；登录与账号身份均以微信 OpenID 为基础。
- 角色分为普通用户、管理员、超级管理员。
- 普通用户只能点菜和查看自己的订单；管理员可管理菜品、分类和订单；超级管理员可额外管理其他用户的管理员权限。
- 前端只负责显示入口，真正的权限判断必须由云函数完成，避免用户绕过页面限制。

## 已完成能力

- 菜单分类、搜索、菜品详情、备注、购物车、优惠券和库存校验。
- 提交订单与订单状态：制作中、已完成。
- 用户订单与历史订单查看。
- 菜品新增、编辑图片/简介/价格、上架下架、售罄和每日库存管理。
- 分类管理、管理员订单处理。
- 微信登录与角色权限校验。
- 体验版邀请好友测试。

## 接下来规划

1. 管理员账户管理：超级管理员可授权或撤销管理员权限，并停用或恢复普通用户账号。
2. 菜品图片管理：管理员可从相册选择或拍摄照片，上传到微信云存储后在用户点菜列表展示；菜品详情和购物车继续保持简洁，不展示照片。
3. 家庭体验验收：邀请家人完成“登录、点菜、下单、管理员完成订单”的完整测试。
4. 订单归档：稳定使用后，保留最近 180 天订单；旧订单先导出备份，再由管理员确认清理。
5. 可选增强：收藏菜品、简单统计、优惠券管理。它们不是家庭试用的必需功能。

## 长期演进蓝图（已确认，暂不实施）

### 第一阶段：多商家架构

- 项目后续向“多商家独立使用”演进，采用一套系统服务多家店铺的数据隔离模式，不复制多套代码。
- 这类架构的专业名称是“多租户架构”：每条业务数据会归属一个店铺，后续菜单、订单、库存、用户权限和报表都应按店铺隔离。
- 在微信原生小程序、微信云开发、云数据库和云存储中完成 `shopId` 数据隔离、角色权限、订单流转、库存控制和基础经营报表。
- 正式实施前必须先完成方案评估、数据隔离与权限风险说明、分阶段迁移蓝图，再开始修改代码。

### 第二阶段：uni-app 跨端迁移

- 当前不迁移 uni-app；只有微信版业务稳定、数据结构规范且有明确 App、H5 或其他端需求时再启动。
- 迁移目标是多端运行，必须采用渐进式迁移，不与后端或数据库迁移同时进行。

### 第三阶段：独立后端与 MySQL

- 当前继续使用微信云开发数据库和云函数，不提前迁移 MySQL 或重构独立后端。
- 只有复杂报表、多端统一后端、外部系统接入或数据规模明确需要时，才评估独立后端和 MySQL。
- 当前开发中应保持数据结构、云函数接口和权限校验可迁移，避免前端直接依赖数据库实现。

### 企业化项目优先级

后续按可写入简历的企业化项目方向推进，优先级如下：

1. 多商家架构与店铺数据隔离。
2. 权限系统与管理员职责边界。
3. 基础经营报表。
4. 项目文档、架构说明、验收记录与简历材料。
5. 最后才评估 uni-app 和 MySQL 迁移。

这些方向属于后续迭代目标，不应触发当前项目的大重构。

简历按“一个主项目，分阶段演进”呈现：第一阶段为微信原生小程序 + 云开发的多商家能力；第二阶段为 uni-app 跨端迁移；第三阶段为独立后端 + MySQL 架构升级。

详细的阶段、数据模型、权限设计、迁移、测试和回滚方案见 [[多商家与跨端演进路线图]]。

## 数据集合

| 集合 | 内容 |
| --- | --- |
| `users` | 微信 OpenID、昵称、角色、启用状态 |
| `categories` | 分类名称、排序 |
| `dishes` | 菜名、价格、图片、简介、分类、库存、上架与售罄状态 |
| `orders` | 订单归属、菜品快照、备注、金额、状态、创建时间 |

订单会保存下单当时的菜品名称和价格。因此即使之后修改菜价，旧订单仍保留原来的内容。

## 技术边界

项目使用微信原生小程序 WXML、WXSS 和 JavaScript，数据与服务端逻辑使用微信云开发的云数据库和云函数。家人手机不直接访问本机 MySQL，因此当前阶段不使用本机 MySQL 或 Navicat。
